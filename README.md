# A Modular Hardware-in-the-Loop Framework for Validating AI-Generated Embedded Firmware

A modular Hardware-in-the-Loop (HIL) testing framework for validating AI-generated embedded firmware against real hardware.

This project investigates whether firmware generated by Large Language Models (LLMs) can be automatically validated through physical hardware rather than relying only on compilation, simulation, or software-level testing.

The current prototype targets an **STM32 Nucleo-F401RE** as the System Under Test (SUT), with an **ESP32** used as an external hardware peripheral for SPI validation.

---

## Research Objective

The goal of this project is to develop a reusable testing framework that can:

1. Execute AI-generated embedded firmware on real hardware.
2. Exercise common peripheral interfaces through physical connections.
3. Detect functional defects that may not be visible through compilation or software-only testing.
4. Provide structured PASS/FAIL results.
5. Support controlled fault injection to evaluate the effectiveness of the test framework.
6. Provide a foundation for automated validation of firmware generated by AI models.

The broader research workflow is:

```text
LLM
 │
 ▼
AI-Generated Embedded Firmware
 │
 ▼
Compile & Flash
 │
 ▼
Physical Hardware
 │
 ▼
HIL Test Framework
 │
 ├── GPIO Tests
 ├── SPI Tests
 ├── I2C Tests
 └── Fault Injection
 │
 ▼
PASS / FAIL + Diagnostics
```

## Framework Architecture

The framework is organized into three major layers:

```text
┌──────────────────────────────────────────────┐
│              Test Framework                  │
│                                                │
│  Test Runner                                  │
│  Test Matrices                                │
│  Fault Injection                              │
└──────────────────────┬───────────────────────┘
                        │
                        ▼
┌──────────────────────────────────────────────┐
│        Hardware Abstraction Layer             │
│                                                │
│  HAL GPIO                                     │
│  HAL SPI                                      │
│  HAL I2C                                      │
└──────────────────────┬───────────────────────┘
                        │
                        ▼
┌──────────────────────────────────────────────┐
│              Target Hardware                  │
│                                                │
│        STM32 Nucleo-F401RE                    │
│       GPIO / SPI / I2C peripherals            │
└──────────────────────┬───────────────────────┘
                        │
                        │ Physical interface
                        ▼
                External Hardware
                     ESP32
```

The separation between the generated firmware and the testing infrastructure is intentional. The AI-generated firmware acts as the System Under Test (SUT), while the HIL framework provides the independent mechanism for exercising and evaluating its behavior.

## Current Hardware Setup

**System Under Test**
- STM32 Nucleo-F401RE
- STM32F401RE microcontroller
- STM32 HAL, built with STM32CubeMX / STM32CubeIDE

**External HIL Device**
- ESP32, configured as an SPI slave
- Used as a physical SPI test peripheral

### SPI Connection

| Signal | STM32     | ESP32   |
|--------|-----------|---------|
| MOSI   | SPI1 MOSI | GPIO 23 |
| MISO   | SPI1 MISO | GPIO 19 |
| SCLK   | SPI1 SCLK | GPIO 18 |
| CS     | PB6 / D10 | GPIO 5  |
| GND    | GND       | GND     |

> **Important:** The CS mapping is explicitly handled by the framework. On the Nucleo-F401RE Arduino header, D10 corresponds to PB6.

## AI-Generated Firmware

The firmware under test is generated using ChatGPT.

The generation process uses an **interface-constrained** approach: the required function names and interfaces are provided in the prompt so that the generated firmware can be integrated with the HIL framework, while the peripheral implementation itself is left to the LLM.

For example, the generated firmware exposes peripheral operations such as:

```c
int ai_gpio_write(...);
uint8_t ai_gpio_read(...);

int ai_spi_transfer(...);

int ai_i2c_write(...);
int ai_i2c_read(...);
```

The HIL framework does not depend on the internal implementation of these functions. Instead, it evaluates their observable behavior on the physical target hardware. This allows the framework to evaluate different implementations while maintaining a common testing interface.

## Hardware Abstraction Layer

The Hardware Abstraction Layer (HAL) provides a boundary between the test framework and the underlying STM32 hardware.

Current abstraction modules:
- `hal_gpio.c`
- `hal_spi.c`
- `hal_i2c.c`

The purpose of this layer is to prevent individual tests from being tightly coupled to STM32 HAL implementation details:

```text
Test
 │
 ▼
hal_spi_transfer()
 │
 ▼
STM32 HAL
 │
 ▼
SPI1
 │
 ▼
Physical SPI bus
```

This architecture allows the testing infrastructure to remain relatively independent of the implementation of the firmware being evaluated.

## SPI Validation

SPI is currently the most developed HIL test case. The framework uses a structured request/response protocol.

**Request:** `A5 01 55 F1`

| Byte | Meaning        |
|------|----------------|
| A5   | Frame header   |
| 01   | Command        |
| 55   | Payload        |
| F1   | XOR checksum   |

**Expected response:** `5A 81 55 8E`

| Byte | Meaning         |
|------|-----------------|
| 5A   | Response header |
| 81   | Response code   |
| 55   | Payload         |
| 8E   | XOR checksum    |

The ESP32 is configured as an SPI slave and validates incoming frames before producing the response.

Example successful STM32 output:

```text
[TEST][SPI] Starting
TX: A5 01 55 F1
RX: 5A 81 55 8E
[TEST][SPI] RESULT: PASS
```

### SPI Fault Injection

The framework also includes controlled fault injection. Current fault types:

- `FI_NONE`
- `FI_SPI_CORRUPT_TX`
- `FI_SPI_CORRUPT_RX`
- `FI_SPI_BAD_HEADER`
- `FI_TIMEOUT`

Fault injection allows us to intentionally introduce errors into the communication path and verify that the HIL framework detects them:

```text
Normal SPI                        Faulty SPI
     │                                 │
     ▼                                 ▼
Correct response              Injected RX corruption
     │                                 │
     ▼                                 ▼
    PASS                       Checksum mismatch
                                       │
                                       ▼
                                     FAIL
```

This is important because a useful validation framework should not only demonstrate successful execution — it should also demonstrate that known defects are reliably detected.

### SPI Test Matrix

| Test             | Purpose                                        |
|------------------|-------------------------------------------------|
| `SPI_NORMAL`     | Verify normal communication                     |
| `SPI_CORRUPT_RX` | Verify detection of corrupted received data     |
| `SPI_CORRUPT_TX` | Verify handling of corrupted transmitted data   |
| `SPI_BAD_HEADER` | Verify protocol/header validation               |
| `SPI_TIMEOUT`    | Verify handling of failed/timeout transactions  |

Example output:

```text
=== SPI TEST MATRIX ===

SPI_NORMAL ............ PASS
SPI_CORRUPT_RX ........ PASS
SPI_CORRUPT_TX ........ PASS
SPI_BAD_HEADER ........ PASS
SPI_TIMEOUT ........... FAIL
```

The timeout case is intentionally useful during framework development because it demonstrates that the test infrastructure can distinguish between successful communication and a failed transaction.

## Test Runner

The test runner provides a common execution and reporting mechanism. Test suites are registered independently:

- GPIO Test Matrix
- SPI Test Matrix
- I2C Test Matrix

The runner executes each registered suite and maintains a running total of tests, failures, and the overall result.

Example:

```text
=================================
     HIL TEST FRAMEWORK START
=================================

=== SPI TEST MATRIX ===

[TEST][SPI] Starting
TX: A5 01 55 F1
RX: 5A 81 55 8E
[TEST][SPI] RESULT: PASS

=================================
Total Tests : 1
Failures    : 0
OVERALL RESULT: PASS
=================================
```

## GPIO Validation

GPIO validation is part of the framework architecture and is intended to verify AI-generated GPIO operations on physical pins.

Planned/implemented scenarios:
- Digital output HIGH
- Digital output LOW
- Digital input state verification
- Incorrect pin configuration
- Input/output behavior validation

The purpose is to determine whether an AI-generated GPIO implementation produces the expected physical pin behavior.

---

## I2C Validation

I2C validation is also part of the framework architecture. Intended test cases:
- Device communication
- Register write
- Register read
- Address validation
- Transaction failure detection
- Timeout/error handling

An external I2C device can be used as the physical test target.

## Why Hardware-in-the-Loop?

Embedded firmware can compile successfully while still containing functional defects:

```text
                AI-generated code
                       │
                       ▼
                Compiles successfully
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
 Software validation             Real hardware
        │                             │
        ▼                             ▼
      PASS                    Wrong GPIO state
                               Wrong SPI timing
                               Wrong I2C address
                                       │
                                       ▼
                                Actual defect
```

HIL testing provides an additional validation layer by observing behavior on real hardware.

## Research Contribution

The project investigates a modular approach for validating AI-generated embedded firmware through real hardware, organized around four objectives:

**1. Survey existing HIL approaches**
Study existing Hardware-in-the-Loop methodologies used in embedded systems and identify limitations when applied to AI-generated firmware.

**2. Design a Hardware Abstraction Layer**
Develop reusable abstraction interfaces for common embedded test scenarios: GPIO, SPI, I2C.

**3. Build a HIL prototype**
Develop a physical prototype capable of executing automated tests against firmware running on an STM32 target.

**4. Develop testing methodologies for AI-generated firmware**
Use controlled faults and multiple test scenarios to evaluate whether the framework can detect functional defects in generated embedded code.
